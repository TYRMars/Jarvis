# Sync Jarvis Projects into Skills

This skill drives `scripts/sync_projects.sh`. The script fetches
`GET /v1/projects` from the configured Jarvis server, then writes
one `SKILL.md` per project under
`examples/plugins/jarvis-control/skills/projects/<slug>/`. Each
generated skill bakes in the project's `id`, `slug`, `name`, and
`tags` so a subsequent ask like "start the next requirement on
Acme" routes directly to the right ids — no fuzzy-matching by name
at request time.

## When to run it

- The user explicitly asks for sync ("sync", "regenerate",
  "refresh the project skills", "/jarvis-sync").
- The user just created a Project via the web UI / REST and wants
  it reachable from Claude Code.
- The user says a project is missing — confirm the project actually
  exists on the server first (`GET /v1/projects`), then sync.

Do **not** auto-sync on every chat turn. It hits the server and
rewrites files on disk; the overhead is small but it's still a
side effect.

## How to run it

```bash
bash examples/plugins/jarvis-control/scripts/sync_projects.sh
```

`--dry-run` previews the write set without touching the disk:

```bash
bash examples/plugins/jarvis-control/scripts/sync_projects.sh --dry-run
```

The script prints one line per project:

- `wrote    <slug>` — fresh write / overwrite.
- `pinned   <slug>` — existing skill has `jarvis_autogen: false`
  in its frontmatter; left untouched.
- `removed  <slug>` — autogen skill whose project no longer
  exists / is archived on the server.
- `kept     <slug> (not autogen)` — hand-edited skill kept even
  though its project is gone (operator's call to clean up).

## What the generated skills do

Each `skills/projects/<slug>/SKILL.md`:

- Carries `name: jarvis-project-<slug>` and a description that
  mentions both the project name and the slug.
- Pins `jarvis_project_id`, `jarvis_project_slug`,
  `jarvis_project_name`, and `jarvis_synced_at` in frontmatter.
- Lists the most common asks for that project (show board, start
  next, approve, reject, dispatch reviewer, show memory) with the
  exact endpoint to hit.
- Defers all write actions to the `jarvis-runs` skill — so the
  per-project skill is really about *locking in context*, not
  duplicating logic.

## Pinning a hand-edited skill

If you customised a generated skill (extra guardrails, a different
phrasing) and want re-runs of sync to leave it alone, add this to
its frontmatter:

```yaml
jarvis_autogen: false
```

The sync script greps for that exact line and skips the file.

## Failure modes

- **Server unreachable** — `jarvis_get /v1/projects` returns
  non-2xx. Sync prints the failure and exits 1 without touching
  any file.
- **`jq` missing** — install `jq` (the script depends on it). The
  helper prints a friendly message and exits 127.
- **`project store not configured` (503)** — the Jarvis binary is
  running but `JARVIS_DB_URL` isn't set, so there's nothing to
  list. Tell the user to set `JARVIS_DB_URL` (or accept the
  default JSON-file store) and restart Jarvis.

## After sync

Tell the user how many projects were written and point at the
new `/jarvis-project-<slug>` skills. They become discoverable as
soon as Claude Code reloads the plugin's skill catalog — the user
may need to `/reload` or restart the session depending on how the
plugin was installed.
