# jarvis-control — Claude Code plugin

Drive a running [Jarvis](https://github.com/zhangjianan/Jarvis)
server from Claude Code. Lists Projects, inspects Requirements,
starts runs, approves/rejects triage candidates, dispatches the
reviewer subagent, and generates one Skill per Project so
`jarvis-project-<slug>` invocations route to the right ids without
the user having to remember any UUIDs.

## What's in the box

```
jarvis-control/
├── .claude-plugin/plugin.json    # Claude Code manifest
├── plugin.json                   # Same shape, kept at root for Jarvis's
│                                 # own plugin manager (examples/plugins/...)
├── skills/
│   ├── jarvis-projects/          # Read-only: list / inspect
│   ├── jarvis-runs/              # Write-side: start / approve / reject / review
│   ├── jarvis-project-sync/      # Drives the sync script
│   └── projects/                 # Autogenerated per-project skills land here
├── commands/
│   ├── jarvis-sync.md            # /jarvis-sync slash command
│   └── jarvis-status.md          # /jarvis-status slash command
├── scripts/
│   ├── jarvis_api.sh             # curl + jq helpers (sourced by other scripts)
│   └── sync_projects.sh          # Pulls /v1/projects → writes skills/projects/<slug>/SKILL.md
└── README.md
```

## Install

### Into Claude Code

Claude Code looks for `.claude-plugin/plugin.json`. From a clone of
this repo:

```bash
# Linux / macOS
ln -s "$(pwd)/examples/plugins/jarvis-control" ~/.claude/plugins/jarvis-control
```

Or copy the directory. Then restart Claude Code (or `/reload` if
your build supports it). You should see three skills under the
plugin's namespace plus the two slash commands.

### Into Jarvis itself

Jarvis's `PluginManager` reads `plugin.json` at the root (this repo
already keeps it dual-rooted). To install:

```bash
# Pointing JARVIS_PLUGIN_ROOT at this directory, or copying it under
# the configured plugins root, will pick up the skill list.
```

The skills work the same in both runtimes — they only depend on
`bash`, `curl`, and `jq`.

## Configure

```bash
export JARVIS_BASE_URL=http://localhost:7001   # default
export JARVIS_TOKEN=...                        # optional bearer
```

Smoke test:

```bash
source examples/plugins/jarvis-control/scripts/jarvis_api.sh
jarvis_health
```

## Usage

### Quick tour

| Ask                                               | Skill / command                   |
|---------------------------------------------------|-----------------------------------|
| "what projects are on the server?"                | `jarvis-projects` skill           |
| "what's on the Acme board?"                       | `jarvis-projects` (or per-project skill once synced) |
| "approve the 'fix login' requirement"             | `jarvis-runs` skill (writes)      |
| "start the next ready requirement on Acme"        | `jarvis-runs` skill               |
| "regenerate the per-project skills"               | `/jarvis-sync`                    |
| "give me a one-shot server status"                | `/jarvis-status`                  |

### Generating per-project skills

```bash
bash examples/plugins/jarvis-control/scripts/sync_projects.sh
```

For every non-archived project on the server, this writes:

```
skills/projects/<slug>/SKILL.md
```

…with `jarvis_project_id` / `jarvis_project_slug` /
`jarvis_project_name` baked into the frontmatter. The generated
skill defers all write actions to `jarvis-runs` — it's there to
**lock in context** so you never have to specify the project id by
hand mid-conversation.

To stop a generated skill from being overwritten on re-sync, edit
its frontmatter to `jarvis_autogen: false`.

`--dry-run` previews the write set without touching disk.

## Endpoints used

All routes are stable parts of Jarvis's public HTTP API; see the
top-level [CLAUDE.md](../../../CLAUDE.md) for the full surface.

Read-only:
- `GET /health`
- `GET /v1/workspace`
- `GET /v1/projects` / `GET /v1/projects/:id_or_slug`
- `GET /v1/projects/:id_or_slug/runs`
- `GET /v1/projects/:id_or_slug/memory`
- `GET /v1/projects/:id/requirements?triage_state=...`
- `GET /v1/requirements/:id/runs` / `GET /v1/requirements/:id/activities`
- `GET /v1/runs/:id`
- `GET /v1/chat/runs`

Write:
- `POST /v1/requirements/:id/runs`
- `POST /v1/requirements/:id/approve`
- `POST /v1/requirements/:id/reject`
- `POST /v1/requirements/:id/review`
- `PATCH /v1/runs/:id`
- `POST /v1/runs/:id/verification`
- `POST /v1/runs/:id/verify`

## Why a plugin instead of an MCP server?

Both are viable; this plugin chose Skills + shell scripts because:

- The wire surface is plain REST + JSON. A curl/jq wrapper is the
  smallest possible adapter.
- The interesting part is the *prompting* — when to dispatch the
  reviewer, when to approve vs ask, how to read the kanban — which
  is exactly what Skills are for.
- Per-project Skills give Claude Code first-class
  fuzzy-matching at activation time ("operate on Acme" →
  `jarvis-project-acme`) without re-implementing routing.

If you'd rather expose the same surface as MCP tools, add an
`mcp_servers` block to `plugin.json` pointing at a thin MCP
adapter and the skills can call those tools instead of curl.
